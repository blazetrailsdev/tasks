# Generate alias attributes from `aliases_by_attribute_name`, not the inverse `attribute_aliases`

## Context

Raised in review of PR #6838 (RFC 0106 wave 4c-b part 3), which converged
`generate_alias_attribute_methods` / `alias_attribute_method_definition` and
wired ActiveRecord's lazy-alias override, but left the sweep walking the wrong
registry.

**Rails** (`activerecord/lib/active_record/attribute_methods.rb:132-137`):

    ActiveSupport::CodeGenerator.batch(generated_attribute_methods, __FILE__, __LINE__) do |code_generator|
      aliases_by_attribute_name.each do |old_name, new_names|
        new_names.each do |new_name|
          generate_alias_attribute_methods(code_generator, new_name, old_name)
        end
      end
    end

**trails** (`packages/activerecord/src/attribute-methods.ts:458`) walks
`attributeAliases` (`new_name => old_name`) instead.

This is **not** merely a different grouping of the same pairs. The two
registries have different inheritance semantics:

- `aliases_by_attribute_name` is a per-class ivar
  (`activemodel/lib/active_model/attribute_methods.rb:382-384`) that the
  `inherited` hook **resets to nil on every subclass**
  (`activemodel/lib/active_model/attribute_methods.rb:387-394`). So a subclass's
  `generate_alias_attributes` generates only the aliases declared ON that
  subclass — the parent's were already generated by the
  `superclass.generate_alias_attributes` cascade at `:128`.
- `attribute_aliases` is a `class_attribute`
  (`activemodel/lib/active_model/attribute_methods.rb:~72`), so it INHERITS.

Walking the inverse map therefore makes every subclass re-generate every
inherited alias, with `override: true`, giving the subclass its own descriptor
where Rails leaves it inheriting the parent's.

trails' own `aliasesByAttributeName`
(`packages/activemodel/src/attribute-methods.ts:492-501`) does **not** yet
match Rails either: it copy-on-writes the parent's entries instead of starting
empty, so simply swapping the AR loop onto it would not reproduce Rails'
semantics.

## Converged shape

- `packages/activemodel/src/attribute-methods.ts` — make
  `aliasesByAttributeName` mirror the `inherited` reset: a class with no OWN
  `_aliasesByAttributeName` starts EMPTY, not as a copy of the parent's. JS has
  no `inherited` hook (see CLAUDE.md, "Module mixins"), so this is the
  own-property idiom the rest of the port uses for per-class ivars, not a copy.
- Export `aliasesByAttributeName` from `@blazetrails/activemodel` (it is Rails'
  `aliases_by_attribute_name`, a real upstream name — `moved`, not novel
  surface, for `parity:api:extra`).
- `packages/activerecord/src/attribute-methods.ts` — `generateAliasAttributes`
  walks it as Rails does, and the `attributeAliases` deviation comment at
  `:458` is deleted:

  for (const [oldName, newNames] of aliasesByAttributeName(this)) {
  for (const newName of newNames) {
  generateAliasAttributeMethods.call(this, codeGenerator, newName, oldName);
  }
  }

## Watch out

`attribute-methods.trails.test.ts > an inherited generated attribute method
does not suppress the subclass's own generation` asserts the CURRENT behaviour
(the alias inherited from `Middle` is regenerated on `Leaf`). Re-derive it
against Rails: with the reset, `Leaf.generate_alias_attributes` has an empty
`aliases_by_attribute_name`, so the assertion about
`isInstanceMethodAlreadyImplemented("nickname")` needs re-basing onto what Rails
actually produces. Do not change the test NAME.

## Acceptance criteria

- [ ] `generate_alias_attributes` walks `aliases_by_attribute_name`, grouped
      `old_name => [new_names]`, mirroring `attribute_methods.rb:132-137`.
- [ ] `aliasesByAttributeName` starts empty per subclass, mirroring the
      `inherited` reset at `activemodel/attribute_methods.rb:387-394`.
- [ ] A subclass no longer re-generates an inherited alias.
- [ ] `pnpm parity:api:calls` / `:args` green; `pnpm parity:api:extra --package
  activerecord` and `--package activemodel` show no new NOVEL surface.
- [ ] SQLite, PostgreSQL and MySQL/MariaDB lanes green.
